# MAPA Console Android — supervised acceptance

Run the fault-injection cases below only in a disposable isolated test environment with synthetic identities. Do not generate fictional incidents in the real ASR workspace. Real crew onboarding follows MAPA-CREW-START-GUIDE.html and uses actual reviewed assignments; never send an ambulance or call a patient merely for a software test.

1. Deploy the native mobile module into the same Laravel backend used by the chosen Windows console. Keep the same native company, user, driver, vehicle, order and place IDs. Configure trusted HTTPS reachable from the test phone.
2. Install `MAPA-Console-Android-pilot.apk` (version code 14). Verify a fresh install preselects `https://mapa-asr-health.pages.dev`, an existing deliberate server selection is retained, and the former command server/token cannot be inherited. Confirm the APK updates the existing pilot without a signing conflict.
3. Sign in with a native crew account linked to one driver and ambulance. Check the displayed native IDs against the console. A second company or driver must not see or mutate this driver's orders, GPS or duty.
4. Tap Start duty and inspect the sharing consent before confirming. Grant notifications and precise location; verify a real fix updates that same native driver and vehicle in the existing console. Check device time, accuracy, GPS-off behavior, stale fixes, weak signal and reconnect. Stored vehicle coordinates without fix time must not be labelled live GPS. Lose a GPS response after commit, restart the app, and verify exactly the same key/payload recovers the receipt. A confirmed cached fix must not be posted again under a new key. Change phone session or resource binding and verify old GPS is never replayed.
5. Create and assign one synthetic ambulance order in the existing console. Verify the phone lists its native order ID, addresses and current native status. Verify a notification while the foreground duty service runs; posting a notification must not acknowledge an order.
6. Acknowledge explicitly only for `can_acknowledge: true`; assigned but undispatched orders and missing/string flags must have no acknowledgement control or actionable alert. Confirm the backend receipt and revised order. For a supported single-destination ASR trip, verify only the next configured step appears after acceptance. Custom/proof/extended workflows must have no next activity.
7. Use further synthetic dispatched calls with `can_acknowledge: true` to test ACK acceptance separately in airplane mode and with a lost server response. Reconnect and verify the outbox retries the same action ID/body/revision, shows no confirmed acceptance before a receipt, and removes the update only after confirmation. A competing console change should produce a reviewable conflict. Repeat immutable retry and conflict checks for start, transport and completion. A missing handover confirmation must reject completion; an exact accepted completion retry must recover its receipt without a duplicate tracking entry.
8. Reassign the driver or vehicle, change company membership, revoke the phone session, disable access and expire the session. Verify current permissions are checked and pending actions cannot cross bindings or servers. Check that earlier assignment actions remain saved, appear only as a neutral held count, expose no old order details and are not described as all up to date.
9. Sign in as hospital, administrator and super administrator. Hospital sees only its linked place. None can start crew GPS. Administrative and hospital writes absent from native capabilities must not appear as working phone controls.
10. Confirm photo/proof, unsupported multi-stop actions and completion gates cannot be bypassed. Enable new features only when the same native backend provides authorization, validation and explicit contracts.
11. Test stopping duty during an active order; server denial must keep sharing active. Test sign-out, reboot, package update, force-stop, notification-channel disabled, screen lock and device battery policies. Reboot reminders must never claim GPS restarted itself.

Trip acceptance: test the advertised step with offline, uncertain-receipt, stale revision, wrong tracking owner, wrong session GPS and current-job mismatch cases. After acceptance, a fresh non-mock GPS receipt from this session is required. Completion requires explicit receiving-team handover confirmation. Verify the native web timeline, status and released current job. Proof and waypoint requirements must never be bypassed.

Record phone model, Android version, APK SHA256, native backend version, server origin, authorized account IDs, expected/observed results and any unresolved defects. Never record staff passwords, bearer tokens or patient data in the test report.

Pending release work: always-on hosting (the current backend still depends on the PC), real device acceptance, owned release keys/update distribution, backup/monitoring/retention policy, native hospital/proof extensions and FCM if required. A successful APK build alone is not production commissioning.
Crew interface review: verify English default, Telugu selection and persistence after closing/signing out; inspect wrapping at normal and enlarged Android font sizes. Compare exact order IDs, names, addresses and native activity codes before/after the language change. Check accepted-call priority, assigned-but-undispatched labels, 58dp actions and fixed bottom navigation. Disabled phone GPS, stale fixes or missing server receipts must never be shown as active transmission. A quiet poll returning 401 must show a sign-in explanation rather than a stale timestamp. Test navigating to a recorded name when its address is empty, and show an explanation if neither is available. No phone or emulator was attached during the source/unit-test pass.
### 1.9 sync and travel inspection

- Sign into the shared origin with the crew account supplied separately by the administrator; the web administrator account must not be used to impersonate a driver. Confirm the native driver/vehicle IDs in Account → Connection details.
- With a synthetic crew and ambulance, start duty outdoors, wait for **GPS is being shared**, then open Travel record. Compare its last device timestamp, server receipt, accuracy and coordinates with the web operator travel view. Walk a short safe test route while carrying the phone. The record concerns the device, not a verified person.
- Switch location off, enable airplane mode for more than two minutes, reconnect, then stop duty. The display must not claim continuous travel across gaps or a completed call. Evidence history remains visible only within the current authorized binding and 200-point / 24-hour window.
- Using Android's explicit development mock-location facility on a test phone, confirm **Mock location is not shared** and that no mocked point is submitted. Disable it and resume real observations. OS flags alone do not prove absence of spoofing.
- Assign a clearly marked test call using the new operator tab. Confirm the same call ID, verified pickup pin, landmark, access directions and caller-reported details reach this crew. Navigation should open the coordinate pin; a missing pin must fall back to the supplied address with no invented coordinates.
- Record Android model/version, foreground notification, precise-location permission, screen-lock result, web/API evidence and observed gaps. Never put passwords or patient information in the report.
