## Startup, recovery and backups

All services use `restart: unless-stopped`; enable `docker.service` at boot. This restarts crashed processes and restores running containers after boot, but does **not** restart a process that is hung yet still running. External monitoring must alert for that case. Do not install a blind database restart loop. An administrator stopping a service intentionally keeps it stopped.

`backup.sh` uses encrypted restic off-server storage, preserves database, uploads, application/provider configuration and the runtime manifest, and never stops operational services. It explicitly loads `compose.yml`, `compose.override.yml` and `staging.yml` under project `mapa-vps`, and checks both mounted volume names against the configured authoritative names before any dump. Storage credentials and the restic password are excluded from the payload; preserve the recovery key separately. The service uses the actual `/opt/mapa-staging/release` path. Install the service and timer only after configuring root-readable `private/backup.env`, initializing the operator's remote repository once and manually verifying one successful backup and isolated restoration. These revised files are local candidates until installed and verified. The timer runs daily at 20:00 UTC (01:30 IST next day). The intended data-loss window is approximately 24 hours only while every scheduled backup succeeds; failed jobs extend it. Choose a shorter interval or database point-in-time recovery if operations require less.

The online SQL dump is transaction-consistent, but uploads copied afterward are **not an atomic matching snapshot**. Preserve immutable uploaded files and allow no deletion during capture, or schedule a coordinated writer pause/storage snapshot for strict consistency. Validate trip-photo references after every restore rehearsal. The script neither deletes remote snapshots nor claims point-in-time recovery. Define retention separately (e.g. daily/weekly/monthly copies after storage sizing) and review deletion rules before enabling pruning. Backup failure is visible in systemd; wire alerts for failed jobs and an older-than-26-hour `/var/backups/mapa/last-success`. Store the image/release artifact independently by digest because the backup does not include Docker images.

## Restore rehearsal (never the live project)

Use a separate isolated host/project with no public ports, no provider egress and all push/WhatsApp/device flags disabled. Run `restic check`, restore one snapshot into a fresh private directory and verify `SHA256SUMS`. Load the recorded image digest, initialize an empty database and import SQL; validate archive members before restoring uploads. Never execute imported shell/config content. Start privately with the original APP_KEY, then verify schema counts, owner login, company restrictions, private photo retrieval, attachment references and app workflows. Record time-to-restore and missing data privately. Destroy rehearsal resources only after explicit review. A successful backup command alone is not a restore test.

The local `verify-backup.py /PRIVATE/RESTORED/PAYLOAD` performs the integrity step before any extraction/import. It requires all backup components and `compose.override.yml`, rejects missing/unlisted files, changed checksums, storage-key payloads, path traversal, archive duplicates, symlinks, hard links, devices and excessive archive sizes. It reads but never extracts or executes a payload. Its result explicitly leaves database restore and application acceptance false. The SQL can still contain commands; import only into a disposable isolated database with no host mounts or network egress. Do not copy restored Compose files into the live release or run their contents.
