MAPA hospital background alerts — addition, 4 October 2026

Hospital support is implemented in the optional Firebase build and backend.
It is NOT commissioned: no customer Firebase project exists yet. Ordinary
APKs including 1.13.1 contain no Firebase SDK and cannot receive FCM in the
background. Do not claim the signed fallback APK has background alerts.

Apply additive migration 2026_10_04_000008_create_mapa_hospital_push_tables.php
only after a backup and deployment review. It creates separate encrypted
hospital device tokens and provider-acceptance receipts. Existing crew push
columns and targets are unchanged. MAPA_HOSPITAL_PUSH_ENABLED defaults false;
both that flag and MAPA_MOBILE_PUSH_ENABLED must be enabled when ready.
HospitalHandoverService queues HospitalPushObserver only after a new onboard
report commits; repeated submission does not enqueue another event. Queue
workers need the same source, configuration and private credential mount.

An authenticated hospital phone uses the existing /push, /push/register and
/push/unregister endpoints. Its hospital/place, tenant and session are derived
from the server binding, never supplied by the app. At delivery the worker
rechecks session expiry/revocation, credentials, membership/MFA eligibility,
binding/place, current trip destination/assignment and unacknowledged report.
Training records, ended trips, changed destinations and acknowledged reports
are not delivered. Hints expire in 120 seconds, share hospital collapse key,
and have backend delivery deduplication; exact-once delivery is not promised.

Hospital FCM data includes only kind=mapa_hospital_changed, event_id,
session_tag and issued_at. Android rejects crew/hospital role mismatches,
expired/cross-session hints and additional payload fields. Notification text
is generic: Open MAPA and review Incoming patients. No patient condition,
identity, coordinates or trip ID are sent through FCM. The authenticated
hospital API must be opened to obtain details. Provider acceptance and local
notification creation are NOT hospital acknowledgement or proof of readiness.
The existing Acknowledge/Team ready API actions remain the only receipt of
staff response. Control must escalate if staff do not acknowledge.

30 September 2026

Implemented: authenticated per-session device registration, encrypted FCM token
storage, native assignment hook, after-commit queued FCM HTTP v1 delivery,
short-lived generic phone alert, logout/scope/credential/MFA revalidation,

Not yet commissioned: no MAPA Firebase project, Android Firebase config or

reports push_alerts=false until required configuration and tables exist.
The ordinary dependency-free APK does not include the Firebase SDK.

Required configuration, all from the same operator-owned Firebase project:
1. Register Android package in.asr.ambulance and obtain google-services.json.
   This is Android configuration, not a server private key. Supply its private
   local path to the optional fcm Gradle build; never put service-account JSON
   inside the APK or public downloads.
2. Enable Firebase Cloud Messaging HTTP v1. Provision a service account with
   only the messaging permissions required for this Firebase project. Mount
   the JSON credential read-only into BOTH the native API and queue worker.
3. Set MAPA_FCM_PROJECT_ID and MAPA_FCM_CREDENTIALS_FILE to the project ID and
   in-container credential file path. Keep MAPA_MOBILE_PUSH_ENABLED=false
   while the build, migration and queue setup are being reviewed.
4. Apply only migration 2026_09_30_000003_create_mapa_mobile_push_tables.php
   after backup and review. It creates new module tables; it does not alter
   native users, drivers, vehicles or orders. The root deployment applied this additive migration on
   30 September 2026 after reviewing its SQL; push remains disabled.
5. Deploy the same current App/MapaMobile source to API and queue workers.
   Native Eloquent assignment changes use PushAssignmentObserver. Call Intake
   explicitly invokes assigned(Order) after writing its native assignment.
   Restart/reload only the affected application/queue workers when scheduled;
   never restart the database just to enable push.
6. Enable MAPA_MOBILE_PUSH_ENABLED=true only when the Android Firebase build
   and real linked crew account are ready for supervised acceptance.

Authentication and privacy:
- POST /mapa/mobile/v1/push/register accepts installation_id (UUID) and
  fcm_token. All company, user, driver and ambulance identities are derived
  from the existing opaque bearer session. The endpoint is rate limited.
- GET /mapa/mobile/v1/push reports available/registered to an authenticated
  phone. POST /mapa/mobile/v1/push/unregister revokes that session's alerts.
- Registrations expire with the 12-hour native session; no perpetual bearer
  token is stored. Logout, password/MFA changes, membership disable and native
  driver/ambulance changes are rechecked before provider submission.
- FCM receives ONLY a generic event kind, random-looking event digest,
  session digest and issuance time. No patient, caller number, pickup, order
  ID, driver name or coordinates are included. The notification says to open
  MAPA; the authenticated API supplies current assignment details afterward.
- Provider acceptance is NOT delivery or crew acknowledgement. No alert can
  dispatch, accept or complete a call by itself. Existing acknowledgement and
  travel evidence remain separate native records.
- Training records never trigger the production push sender. Queue failures
  do not roll back dispatch; control must verify the crew acknowledgement.
- Retries may be delivered more than once by the provider. Backend event
  receipts and phone event IDs suppress repeats; exact-once delivery is not
  claimed. Hints expire in 120 seconds and never replace the operator's
  escalation procedure if an assignment is not acknowledged.

Acceptance on each real phone (start with one phone, then increase):

2. Allow notification permission and the MAPA assigned-calls channel; enable

4. Repeat with background app, phone lock, lost-and-restored internet, token

   Play services, no internet, or vendor battery restrictions can stop alerts.
5. Keep an operator backup contact procedure. Test the 25-phone workload;
   simultaneous 25-device capacity has not yet been measured.
