# MAPA native mobile module — isolated pilot core

This module belongs to the **first MAPA console and its existing Laravel/MySQL API**. It does not use the separate ASR website, pairing service, database or 8791 demo. ASR Health is the operating organization; upstream Fleetbase names/licenses remain intact.

## Registration (root integration owner only)

1. Copy this directory to `/fleetbase/api/app/MapaMobile` in the API image. Composer's existing `App\\` namespace resolves the classes. Do not replace upstream packages.
2. Register `App\MapaMobile\MobileServiceProvider::class` from the existing MAPA provider's `register()` method. The provider merges `mapa_mobile` configuration and discovers only this module's additive migration. It never runs migrations, creates accounts or enrolls users itself.
3. Review/run the migration through the normal controlled migration process. It adds five `mapa_mobile_*` tables and changes no native tables. Native UUID references are checked every request; no foreign-key deletion cascade can delete upstream data.
4. Keep `MAPA_MOBILE_ENABLED=false` until company scope, native accounts and explicit bindings have been reviewed. `config('mapa.company_uuid')` supplies the one allowed company. No request chooses or switches company.
5. An operator provisions a disabled binding with the actual native `user_uuid`, company, role and (for crew) matching native `driver_uuid`; hospital uses native `place_uuid`. Verify the native user and company membership are active before enabling. Do not trust self-submitted role IDs. Changes to role/driver/place should increment binding revision and revoke sessions. Exact native resource scope is additionally hashed into sessions, so native vehicle swaps invalidate old tokens even without a revision bump.
6. `superadmin` additionally requires both the native platform User `type=admin` and the UUID explicitly listed in server `MAPA_MOBILE_SUPERADMIN_UUIDS`. A native platform admin is **never automatically enrolled**. An `admin` binding grants company-scoped mobile reads, not platform rights. This initial module has no administrative write endpoint.
7. Serve the API through reachable HTTPS for phones. `localhost:4200` is the console, not the API and not a phone's server address. The APK must use a configured API origin and native email/password. Never embed org API keys, console cookies or broad Sanctum credentials.

No routes are enabled just by copying files. The root integration owner controls registration, migrations, image build and rollout. No production provisioning is performed by the tests below.

## HTTP contract

Base: `/mapa/mobile/v1`. JSON requests. Authenticated routes use `Authorization: Bearer <opaque token>`. Responses and errors are `Cache-Control: no-store`; errors contain `error`. Common statuses: 401 sign in again, 403 role/scope denied, 404 assigned resource unavailable, 409 refresh/review changed state, 422 bad input, 429 rate limit, 503 unconfigured/unavailable.

- `POST /login`: `{email,password,device_name?}` → `{contract:"mapa-native-mobile-v1",token,expires_at,user,capabilities}`. `expires_at` is epoch milliseconds, at most 12 hours. Tokens are random 32-byte values, only SHA-256 hashes persist, maximum five active sessions per binding. Password changes, revoked/expired sessions, disabled membership or changed binding/native scope invalidate access. Login is rate limited per normalized account and IP. Native customer accounts and unverified non-admin accounts cannot sign in. Native user/system/company MFA settings and explicit metadata/options security flags (`two_factor_enabled`, `mfa_required`, `password_reset_required`, `force_password_reset`, `must_change_password`, `password_expired`) fail closed on login **and every session request**. MFA challenge/reset UI is not implemented; these users must use the console. Checks read native settings directly without creating defaults or relying on stale cache.
- `GET /capabilities`: `{contract,user,capabilities}`. User: `{id,name,role,company_id,driver_id,vehicle_id,place_id}`; native public IDs for resources (company_id is native company UUID). Nullable unbound IDs.
- `GET /snapshot`: `{contract,user,capabilities,driver,vehicle,orders,places,server_time}`. `driver={id,name,online,vehicle_id}`; `vehicle={id,name,registration,latitude,longitude}`. Crew reads only its native assigned active orders. Admin/superadmin reads at most 100 recent company active orders. Hospital reads only its bound native Place and no orders/fleet. No patient/caller notes, unrelated contacts or arbitrary native model serialization are exposed.
- Order: `{id,internal_id,status,revision,acknowledged,can_acknowledge,pickup,dropoff,next_activities}`. Places are `{id,name,address}` or null. `can_acknowledge` is an explicit boolean using the same current native assignment/dispatched/status policy as the acknowledgement endpoint. Created/scheduled and terminal orders cannot be acknowledged. `next_activities` advertises only the next supported configured trip step after acknowledgement. `activity_unavailable_reason` explains unsupported workflow requirements.
- `POST /logout`: `{}` → `{ok:true}`; revokes only this module session.
- Crew `POST /duty`: `{action_id,online:boolean}`. Sets native Driver and its currently assigned Vehicle explicitly; it never blindly toggles duty. Ending duty is blocked while a dispatched active order remains.
- Crew `POST /gps`: `{action_id,latitude,longitude,recorded_at,accuracy_m,heading?,speed_mps?}`. Requires online duty and native vehicle assignment. Fresh fixes only (at most 5 minutes old, at most 30 seconds future, accuracy ≤100m, monotonically newer per driver). Writes native Driver/Vehicle and native Position rows. Native position timestamps remain receipt time; the device time is kept separately in module driver state. Speed is validated but not copied into an undocumented native unit. Location broadcasts occur only after commit.
- Crew `POST /orders/{nativePublicId}/ack`: `{action_id,expected_revision}`. Records genuine acknowledgement without fabricating native activity progression. The native driver/company/vehicle assignment must still match. It also preserves a `mapa_mobile_acknowledgement` object in native order metadata (timestamp and native public driver/vehicle/user IDs) so console-side data retains evidence. Any subsequent external order edit can require a new acknowledgement. An old metadata entry remains historical evidence, not proof that the current revision has been acknowledged.
- Crew `POST /orders/{nativePublicId}/activity`: `{action_id,expected_revision,activity_code,confirmed:true,handover_confirmed?:true}`. Supports reviewed ASR `dispatched → started → enroute → completed` only. Requires current acknowledgement, duty, exact active assignment, tracking ownership and a recent non-mock GPS receipt from the current session after acceptance. Completion additionally requires `handover_confirmed:true`. Native order/tracking/crew audit and receipt are atomic; after-commit cache invalidation updates web reads. No native pre-commit event chain, outgoing completion messages, webhooks or automatic reallocation are invoked. Proof, extended/custom/financial workflows fail closed to the console.

Mutation response: `{ok:true,replayed:false|true,revision?:string}`. Fetch snapshot afterward. `action_id` is 8–100 ASCII letters/digits/underscore/hyphen; UUID is supported. Persist the exact body and path for uncertain retries. The same ID with a changed body/path returns 409. Receipt fingerprints also include the immutable company/user/role/driver/vehicle/place scope: a fresh login after reassignment cannot replay a success for the former ambulance. Same-scope reauthentication can safely retry. Receipts are transactional with the mutation. Exact replay precedes terminal/stale-revision checks, but **never bypasses current identity or native resource ownership**.

## Capabilities and commissioning

`activities` is enabled for assigned crew when `MAPA_MOBILE_TRIPS_ENABLED` is true (default). Per-call next steps additionally require the reviewed workflow shape and current acceptance; clients must never invent stages. `photo_upload`, `hospital_response` and `admin_writes` remain false. `push_alerts` becomes true only with the enabled, configured FCM provider and additive push tables. See [PUSH-SETUP.txt](PUSH-SETUP.txt).

GPS receipts internally bind their session digest without returning that field. Exact receipt replays strip the private field. Trip evidence is a device report and crew confirmation, not independent proof of travel or hospital acceptance. A physical phone and real provider commissioning are still required; isolated tests use no operational writes.

## Tests

Run `php tests/policy.php` for pure invariants. `tests/native.php` boots the installed Laravel app in a separate CLI process and creates **connection-local TEMPORARY schema shadows** of native tables, plus temporary module tables. It copies schema, never live rows. Synthetic users/companies/vehicles/orders use DEMO names and `meta.mapa_demo=true` where the native schema supports metadata. External HTTP/mail/notifications/jobs are faked, the transaction rolls back, and temporary tables are dropped on exit. It does not run migrations. `tests/inspect-native.php` reads column requirements only.

The integration test briefly registers routes in its isolated CLI application to exercise a private in-memory rate limiter; it never registers routes in the serving process or writes live Redis keys. A fixed per-IP bucket rejects the 241st request even when every bearer token is different. Only the native Position `creating` event is allowed through so the genuine UUID initializer runs; other native/domain events remain faked.

Verified on 18 September 2026 against the installed native Laravel/MySQL runtime: **47 policy checks and 81 native integration checks passed; all 10 PHP files passed syntax checks.** Coverage includes all four roles, native MFA/security flag changes during a session, password/expiry/revocation, fixed-IP throttling with rotating bearer tokens, GPS identities/freshness/replay, reassignment across fresh login, native ACK persistence after MySQL JSON normalization, metadata preservation, terminal-state replay and cross-company denial. These are isolated backend checks, not a real-phone or public HTTPS acceptance claim.

Use a temporary container directory to run these tests. Do not run them through Octane or a shared persistent connection. `php -l` checks all module/migration/test files. Tests must finish successfully before the root integrates this module; a successful syntax check is not a provider or production acceptance test.

## Operational limits

No real phone calls, notifications, patient data, provisioning, native account changes, production migrations or external publication are included. Configure shared persistent rate-limit storage across replicas, HTTPS, access/audit/backup policies, retention for session/receipt history and a supervised native-console/APK pilot before operational rollout. Native GPS freshness and downstream fleet dashboards must be commissioned against actual devices. Rollback disables routes first; dropping module tables is a separate destructive operator choice, and does not erase native position/activity history.
